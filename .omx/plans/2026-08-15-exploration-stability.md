# 探索稳定性与策略分阶段计划

日期：2026-08-15

## 当前基线

- 正式自主探索入口：`src/danger_search_robot/exploration/graph_nbv/scripts/graph_nbv_stage_b31_manual_gate_node.py`。
- 正式启动链：`graph_nbv_stage_b31_manual_gate_timed.launch`，默认挂接仿真时间看门狗。
- `4db6ee6` 已推送到 `origin/master`；工作树只有嵌套 `src/Livox-SDK` 的未跟踪构建产物，不属于本阶段修改范围。
- 之前三层完整回退运行已验证传感器、视觉、地图、电梯和结果闭环，但它使用 Gazebo 模型状态改变视点，不能替代真实 Graph-NBV 四房间验收。

## 阶段一：单层四房间稳定基线（15日前）

目标：在固定场景和固定起点下，正式 Graph-NBV 能够完成四个房间的可观测探索，不因一次短暂 TF/地图/导航异常进入无限重试或提前结束。

实现范围：

1. 为地图、TF、目标生命周期、门禁和结束原因增加结构化运行状态。
2. 手动门禁等待连续稳定位姿后再锁定，避免启动瞬态把门方向记录错。
3. 前向区域连续无目标达到阈值后“解锁探索门”，而不是直接宣布任务完成；解锁只改变候选策略，不直接改后退控制。
4. 目标失败后增加短暂恢复冷却、失败计数和安全终止上限，避免快速重复发目标。
5. 保留路径规划与后退控制现有策略，先通过指标确认问题属于探索器、导航还是底层恢复。

验收证据：

- 真实 Graph-NBV 日志中有四个房间/区域的目标到达或扫描记录。
- 每个目标有开始、到达/失败、原因和耗时；失败次数有上限。
- `~runtime_status` 能读到当前阶段、目标、地图/TF 新鲜度、门禁状态和恢复计数。
- 运行结束原因明确为 `FINISHED` 或 `ABORTED_SAFE`，不能只看进程退出码。

## 阶段二：状态机和后退恢复（16–18日）

- 把探索、全局转移、目标恢复、暂停/健康降级、安全停止变成唯一状态机。
- 明确每个状态的进入条件、超时、最大重试次数和退出动作。
- 根据阶段一指标再调整后退/脱困，禁止无证据地扩大倒车距离或持续发布速度。
- 将恢复结果分类为短暂传感器异常、目标不可达、局部规划失败、底层恢复失败。

## 阶段三：比赛闭环（19–20日）

- 接入三层地图切换、电梯幂等迁移、危险源确认和最终返回。
- 固定场景至少做三轮完整回归，并保留每轮摘要、结束原因和 Git commit。
- 完成前核对本地 `HEAD`、`origin/master` 和工作树，不把历史日志当成远端同步证据。

## Git 同步规则

每个阶段只提交相关源代码、配置、测试和文档；不提交 `results/` 下的运行日志、地图和截图，也不处理嵌套 `src/Livox-SDK` 的无关构建产物。每次推送后记录本地与远端 commit 是否一致。
